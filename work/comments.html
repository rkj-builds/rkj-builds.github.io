Comments, brought in-house

Leaving feedback on a design used to need a paid seat on our hosting provider. One seat, per person, per anybody who wanted to say "move this 8px". I built the comment layer into the workspace instead. Eight brand teams run it now.

What a brand is here

Travelopia is a parent company with sister travel brands inside it. Each brand runs its own site, repository and design system, and almost every brand has one designer.

What it cost to say "move this 8px"

Review happened on deployment previews, and the only comment tool on a preview was the hosting provider's own. It requires team membership, so every stakeholder who wanted to leave one comment needed a seat, at $205 each.

It failed quietly. A reviewer clicked the comment affordance, landed on an access-request screen, and the request went to whoever owns the team. Feedback came back as email instead, detached from the pixel it was about, while team owners spent the week declining access for people who wanted to point at a heading.

What replaced it

A comment layer that renders on every page the workspace can show, a full-screen layout or exploration included, because that is where review happens. The browser never holds a database key: it draws pins and calls handlers under the workspace mount, and those handlers decide what the signed-in person may see and write.

  1. The browserDraws the pins, arms the crosshair, opens the panel. Holds no credential of any kind.
  2. <mount>/api/comments/**Installed into every host, dormant until the environment activates them. They check the current Helix user, then scope every read and write to one project and one page path.
  3. Postgres, and an object bucketThe rows, and the attachments beside them. Images and links are first-class, because half of "move this 8px" is a picture.

Six decisions, and why each one

  • No launcher of its own. The button sits in the dock with the designer tools, and that dock is the only thing floating over the page. The layer tells it what to show, it tells the layer which side the panels open on, so a comment panel takes the frame every other tool already uses. A second floating button was a day's less work, and a second language on the page forever. It is also what made the dock worth building properly: a tool is an entry in a registry that a brand switches on or off, so the eighth one is a row in a list rather than another thing in the corner. The dock and that list are the next page.
  • One sign-in, never two. The layer never asks anyone to sign in. If you can open the link you can comment, because page access and comment identity are the same verified user. A separate comment login is what killed the tool this replaced.
  • Your name comes from your work address. rahul.jha@ becomes Rahul Jha without a dialog. Only an address carrying no name gets asked, and then once. Nobody should have to introduce themselves to leave a note.
  • A comment keeps the name it was filed under. Changing your avatar updates your old comments; changing your name does not rewrite them. A thread from March should still read the way March read.
  • Comments are not annotations. A comment is stakeholder feedback with a name on it. An annotation is a designer's private note to an agent that never leaves the machine. Two features on purpose: merging them means either publishing someone's rough notes or asking a stakeholder to think about prompts.
  • Scoped by project and page path. Ten brands share one store, so the scope is the thing that keeps one brand's review out of another's page. It is also the thing that broke, below.

The bug that changed the design

A designer filed about fifty comments across one morning. That afternoon they were gone from the page.

Nothing was deleted. The project name was derived from the deployment's git metadata, and someone had pushed production from the command line, which carries none. The derivation fell through to its default and the site began reading under a project nobody was looking at. Every row sat where it was filed; the page was asking the wrong question.

I re-parented the stray rows, then changed the shape so it cannot recur: no derivation and no fallback. The project name is required, and a missing one reports comments switched off rather than quietly filing them elsewhere.

The useful part is not the fix. The outage was a default doing its job, and a fallback that produces a plausible value is worse than none: the system keeps working, and only the people stop making sense.

How the other brands got it

Eight teams adopted it without me touching eight repositories: one commit against the workspace version, three shared variables linked from the team account, a redeploy.

When a designer reports comments broken, I send them what they have not done rather than fixing their repository. Eight repositories I fix myself are eight I own forever, and a designer who never saw the failure cannot recognise it the second time.

It is almost never the deployment. It is a preview built before the rollout, or local development with the variables missing, so the checklist opens by telling them to read the settings payload rather than the status code. The handler answers honestly; the status code does not.

The reviewer who needed a $205 seat to say "move this 8px" is the reason the whole thing exists.

The block at the top is the layer rebuilt by hand, from its own stylesheet. The one in production runs against a signed-in database, and I am happy to walk through it live.
