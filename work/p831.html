A booking platform that runs a place

My own product. A sports venue takes its bookings through a WhatsApp bot, its staff run the day on a desk, the public books from a widget, and a voice agent books by phone. All four ask the same module what is free.

Mar–Oct 2026MineReact 19, Vercel functions, PostgresLive, in daily use

One answer about what is free

Four surfaces can take a booking and they cannot disagree. The desk, the public widget, the WhatsApp bot and the voice API all call one availability module, and the same module runs on the server when the booking is written.

So the desk never offers a slot the bot has just taken, and a race on the last court comes back as 409 SLOT_TAKEN rather than a double booking.

Recurrence, in three layers

A weekly programme needs a rule for what repeats and something that stops a weekend selling once it has happened. I split those apart on purpose, because the obvious design puts correctness in the cron job.

A dead cron should degrade to "nothing available", never to "book a date that already passed."

// lib/eventRecurrence.js
// THREE LAYERS, deliberately independent:
//
//   1. The rule            — events.recurrence (JSONB).
//   2. Read-time selection — sessionHasStarted() / runEndDate().
//                            THIS is what makes the site correct.
//   3. The nightly roll    — adds supply, retires spent runs.
//                            Pure housekeeping.
//
// The layering is the point. If the cron owned correctness, one missed
// fire would put a past weekend on sale.

Dates that never slip a day

A booking date has no time in it, and a date with no time is the classic off-by-one: stored as midnight UTC, shown in a browser two zones west, it becomes the day before. So every date-only value is formatted with timeZone: 'UTC', and every clock time is formatted in the venue's own zone, named, never the device's.

The venue has no daylight saving, so the slot maths uses a fixed offset. That is a shortcut, so a recurrence rule naming any other zone is rejected outright rather than computed wrongly. The first venue abroad fails loudly on its first save, which is how I want a bug I can already name to behave.

What it is in practice

  • Live since March, and the venue runs on it every day. The data is real, which is why every screen here is in mock mode.
  • 2,900 tests, run with a guard that fails any test file that opens a network connection.
  • A REST API for a voice agent: availability, slots, bookings, with its own key per tenant and rate limits in front of it.
  • Payments, reminders and a register, because a booking tool that cannot take money is a calendar.

Four ways to book, one module that decides. Everything else is interface.
