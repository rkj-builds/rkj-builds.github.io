A ticket is a request to move a number

Tickets arrived as design asks with a wireframe attached. I wrote down how I actually work them as one Claude Code skill, so every ticket runs the same loop and the next one starts where the last one ended.

The loop

Eleven steps. I hold the six that need judgement.

  1. RUN · ASKIntakeTicket, links, comments and attachments copied word for word
  2. ASKSizeS, M or L, with one line of reasoning
  3. ASKMetricOne primary metric, up to three secondary, up to five guardrails
  4. RUNEvidenceRaw data first, then the evidence index
  5. ASKHypothesesEach one with its cites, plus the Challenge block
  6. HELIXDesignOne hypothesis per variant, then the review and states passes
  7. RUNInstrumentationEvents, parameters and hidden attribution fields
  8. ASKMeasurement planA/B or pre/post, sample size, read date, stop rules
  9. ASK ×2ShipThe ticket comment, then the push. Never the merge.
  10. RUNCase studyDesigned to be skimmed and served on the preview
  11. RUN · ASKReadout and logThe result with denominators, and what carries forward
  12. Back to 01. The log entry from step 11 is the first thing intake reads on the next ticket.

What never changes

Four principles, on every ticket

  1. 01Metric firstPrimary, secondary and guardrail metrics are named before any design.
  2. 02Evidence over intuitionAn existing page uses its own data. A new page uses the closest analogue, past tests, competitors and benchmarks.
  3. 03Challenge the briefEvery ticket gets a Challenge block, even when it ends up agreeing with the brief.
  4. 04A case study every timeSized to the ticket, plus a log entry.

The psychology pass

Every friction gets a named bias. Every lift gets a principle.

ETHICS QUESTION 1Would the visitor agree if they saw how it was built?
ETHICS QUESTION 2Does it still work if they know?

A hypothesis that fails either question is dropped, and the Challenge block says why. Named and refused:

  • pre-ticked consent
  • counts on cached availability
  • countdowns that reset
  • confirmshaming
  • costs revealed at payment
  • a hidden cancel
  • forced continuity
  • Zeigarnik nagging
  • a phone number only for sales calls

It fixes itself

When the skill gets something wrong, the fix goes in before the ticket closes

LL-020 → docs/growth/skill/SKILL.md30 Sep 2026 · +2 lines

I asked whether the error states had been thought through. They hadn't, and the case study would have claimed a finished form with no validation.

+ Then a states pass, before any variant is called done: empty and invalid fields, message wording, submit with errors, pending, failure and offline, closed mid-way, keyboard in any pop-up, phone keyboards and autofill.

+ Drive each state in the browser and capture it; a state that was not exercised is not done.
