The skills that build the system

Helix is where the design system is read. The skills are how work gets into it. Fourteen of them, each with one job, and one rule that stops any of them running alone.

2026Mine14 skills, 2 harnesses, 1 sourceClaude Code and OpenCode

Why a skill instead of documentation

Design system rules fail in a specific way. They are written down, they are correct, and nobody reads them at the moment they matter, which is halfway through building something at four in the afternoon.

A skill is the same rules, loaded at that moment. The designer asks for a component; the rules arrive as part of the work, not as a link in the review after it is already wrong. Nothing has to be remembered for the system to hold.

Two ways in, because teams arrive from two places

Most design system tooling assumes a greenfield. Almost nobody is on a greenfield.

  • You already have a production site. Install reads the repository you have. It finds the token files, the component directories and the app router shape that already exist, asks where each one lives, and writes the config to match. Nothing is rewritten and nothing is renamed. The site you ship becomes the design system: the components are the real ones, the tokens are the real ones, and the layouts are pages that were already live.
  • You are starting from nothing. Init runs the other way. Domain, personality, an OKLCH colour ramp, type and spacing scales, themes, then the starter primitives. From there it is explore, approve, promote.
  • The direction is not fixed either. Components first, then compose a page from them. Or a whole page first as a lightweight exploration, approved as a link by someone who will never clone anything, then promoted into components. Both routes end in the same library, which is the only thing that has to be true.

Fourteen skills, grouped by what they are for

  • Getting in. helix-install puts the runtime into a host and re-interviews on every run, so an update is the same command as a first install. helix-design-system-init is the bootstrap for a system that does not exist yet.
  • Diverging. helix-explore is a scratchpad with real tokens and real type, for the half of the job that needs five answers rather than one. It runs permissive on purpose: an exploration that has to pass the full gate is an exploration nobody makes.
  • Converging. helix-exploration-promote is the hinge. It runs a token-gap pass, either proposing a token or snapping the ad-hoc value to one that exists, classifies the pattern as landmark, content or primitive, extracts the API, and only then builds. The exploration is not deleted on success, because it is the visual contract the result gets checked against.
  • Building. helix-component and helix-compose-layout. Both apply to every change regardless of size, including a one-line padding tweak, because small changes are where invariants quietly break.
  • Verifying. helix-design-system-audit owns the rules, helix-a11y owns the accessibility gate, helix-a11y-interactions owns the deeper interaction model, and helix-visual-verify catches the two things an audit cannot see: drift from token snapping, and a missing interaction state.
  • Extending. helix-tool builds a new toolbar tool inside the kit, and refuses to run inside a brand repository.
  • Routing and housekeeping. helix reads the request and pairs the right skills. helix-wireframe sketches page structure. helix-local-prune clears worktrees and dev servers, and never touches origin.

The rule that makes it a system

No build skill loads on its own. Every one of them loads the audit and the accessibility gate in the same response, and the build is not finished until both come back clean.

That is enforced in four places that do not depend on each other: the router's pairing table, each build skill's own description, a hook that re-states it on every message, and a second hook that blocks writes into the runtime directory. Belt and braces on purpose, because the one time it was asserted in only three places, a harness quietly lost it when a script grew a rule and a copy of that script did not.

So there is no door into a build that skips verification, and accessibility is not a phase at the end that gets cut when the sprint is tight.

Headless, and kept that way

The workspace runtime is not owned by the brand that hosts it. It is copied in on install, restored at the start of every session if it has drifted, and a hook blocks writes into it, so a designer cannot quietly fork the browser for one brand.

When a build hits something the runtime cannot do, the skill reports the gap and composes with what exists. It does not write the missing piece locally. That one refusal is what keeps ten brands on one runtime instead of on ten slowly diverging copies of it.

The same source ships to two different agent harnesses. One fix lands once.
