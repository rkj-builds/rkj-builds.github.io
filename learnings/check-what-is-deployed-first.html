Three correct fixes, none of which could run

The new WhatsApp number was dropping every inbound message. I changed the config, then the database, then theorised about Meta. Production was running a nine-day-old commit.

Where
WhatsApp, the second number
Cost
An afternoon, and one right setting overwritten
The rule
A symptom that contradicts the code is a deploy question first. Check the SHA before changing anything.

What happened

We had moved the repository to a new GitHub account. The link between GitHub and Vercel did not survive the move, silently. Merges kept landing, deploys stopped. Nine days later the two-number code existed everywhere except on the server.

Every fix I made was correct for the code I was reading and impossible for the code that was running. One "correction" overwrote a setting that was already right, because I read "not registered to a tenant" as a wrong id when it meant the deployed code had no idea a second number existed.

What it taught us

The fastest check needs no login: the public health endpoint returns the deployed commit. Compare it with main. A frontend bundle hash proves nothing, because a backend-only change leaves it byte-identical.

And a log that reports a refusal without naming what was refused is a log that invites guessing. Add the value to the log before theorising.

The rule now

Symptom contradicts the code: check the SHA. Then read a log that names the actual value. Then change something. The GitHub link was re-made and the repository now has one admin who can see it break.
