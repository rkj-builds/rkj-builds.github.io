The database ran out, not the code

At 11:56 the bot and the dashboard went down hard. Nothing had been deployed. The free database tier had spent its disk budget, and every symptom pointed somewhere else.

Where
The whole product: bot, dashboard, desk
Cost
Hours down, on a Friday
The rule
Three different errors meant one thing. Rule out capacity before blaming a deploy.

What happened

The database runs on Supabase's free tier, on the smallest instance. On 10 October it ran out of Disk IO budget. Checkpoints that took 0.6 seconds took 43. Every query timed out. The API layer could not even load its schema cache, so every route answered 500 or 503.

The dashboard did not say any of that. It said "Too many login attempts. Try again later." The login limiter fails closed by design, so an unreachable database reads as a lockout. We looked at the limiter. Then at the 45 commits a colleague had just pushed. The load had been flat at 80 to 110 requests an hour the whole time. The data had simply outgrown the tier.

What it taught us

Capacity is a live constraint, not a setting. A flat workload on a small instance degrades as the data grows, with no code change to point at.

And symptoms point away from the cause. A login lockout, a 500 and a 503 were one fact in three disguises. An earlier note of ours also claimed the database was on a paid plan; it never was, and that wrong belief cost a whole line of investigation.

The rule now

Before touching code for a production symptom, check the database's health and its budget. Recovery was a fast reboot plus raising one role's statement timeout from 8 to 60 seconds so the API could rebuild its cache, then putting it straight back. The runtime logs now print a database error count per request: 1 is broken, 0 is healthy, and a 401 from an unauthenticated probe is a healthy answer, not a fault.
