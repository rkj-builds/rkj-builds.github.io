A design question is a request for an answer, not a mandate to build it

The inbox needed to show which number a message came in on. I was asked how multi-number inboxes are usually done. I answered, and then built the answer.

Where
The inbox, two WhatsApp numbers
Cost
Two pull requests, reverted
The rule
Ship the smallest change that fixes the report. Name the bigger change in one line and let the owner choose.

What happened

Two pull requests appeared within the hour: a table of tenant numbers, a migration, inbox labels, a notice in the composer. Rahul's response: "Why the hell are you doing all of this? This will break so much. The fix is simple, and you already know it." He reverted both.

The real fix was three files and no migration: record the inbound number on the message, and have desk replies use it.

What it taught us

A question about design is not permission to change the schema. On a product that takes money every day, every migration is a risk the owner has to carry, and a bigger change competes with the bug for the same afternoon.

The rule now

Fix the specific bug. If a broader change looks right, say so in one line and wait. Never open the pull request first.
