Code goes live before its columns exist, every single time

A pull request is merged within minutes. Vercel deploys on merge. The migration is pasted into the database editor whenever a person next sits down. The order is fixed and nobody controls it.

Where
Memberships, every path that creates one
Cost
Enrolment down across the product for the gap between a merge and a migration
The rule
A column from a migration that has not run is omitted, never written as null. Verify migrations by running them.

What happened

New code wrote a new column into every membership row: the sessions total, as null when there was none. The column did not exist yet. Naming a column Postgres does not have fails the whole statement, and all four callers were inserts: the desk, the public signup page, renew and convert all failed.

The same day, a second lesson from the same file: the editor runs a migration as one transaction. A bad check constraint at the bottom took every column above it down with it, and the next script failed with "column does not exist", which looks like a different problem and is the first error in a disguise.

What it taught us

A read that fails degrades a page. A write that fails takes the money with it and looks like the product is down. I made the read path survive it, wrote a paragraph about merge order not being enforceable from code, and introduced the identical hazard on the write path in the next commit.

The rule now

A pending column is omitted from inserts until it exists, which costs nothing because a fresh row defaults to null anyway. A test holds the list of pending columns and the list is updated when the migration is written, not after the outage. Migrations are verified by running them in a local WASM Postgres with the exact row the code builds; the failure reproduces in seconds and no amount of re-reading the diff shows it.
