The route that never reached the code

An attendance endpoint was written, unit-tested and shipped. It never once reached the server code. The request died one layer above it.

Where
Attendance, the kids' programme
Cost
Weeks of zero attendance rows and an afternoon spent on a database that was perfect
The rule
Read the HTTP status before theorising about layers. A 405 rules out the whole application.

What happened

Our API handlers are reached through hosting rewrites written per path depth. Path parameters never match across a slash. The new route was one segment deeper than the deepest rewrite, so it fell to the catch-all, which resolved to no file, and the host answered 405.

There was no server log and no database error, because nothing ran. So we spent the afternoon on the database. I reasoned from "which layer usually breaks" and guessed wrong twice. Driving the browser and reading the response took two minutes and settled it.

What it taught us

A 405 is a routing answer. It rules out the application, the database and the data. The status code was the first fact available and the last one we looked at.

The rule now

Any new API sub-route adds its rewrite in the same change, and a test asserts the rewrite config against every path the router can read, so a missing depth fails the suite.
